# ADR-003：为 SQLite JSON 记录维护派生查询列

## 状态

Accepted

## 日期

2026-07-23

## 背景

Run 和 Step 以 JSON 保存完整领域记录，便于合同演进和事务内原子更新。但 Run 列表、调度、运维和待媒体对账反复使用 `json_extract`，用户列表还需要先读取全部 Run 再在内存筛选和切页。数据增长后，这会放大 CPU、内存和启动成本。

## 决策

- JSON `data` 继续作为完整领域记录的权威来源。
- `agent_runs` 派生维护 `tenant_id`、`external_user_id`、`status`、`lease_until` 和 `updated_at`；`agent_steps` 派生维护 `tool` 和 `status`。
- 创建与事务更新必须在同一个 SQLite 事务内同步写 JSON 和派生列。
- 用户 Run 列表使用 `(tenant_id, external_user_id, updated_at DESC, id DESC)` Keyset 索引和游标，不使用 offset 或全量内存分页。
- 启动迁移只更新派生列缺失的旧记录。列新增和回填在一个事务中完成；重复启动不得重写完整记录。
- 运维、调度和待媒体查询优先使用派生列及覆盖其过滤条件的索引。

## 备选方案

### 继续使用 `json_extract` 和表达式索引

拒绝。表达式在多条查询中容易发生路径或类型漂移，写路径也难以显式验证缓存字段与领域对象同步。

### 完全规范化 Run 和 Step

暂不采用。当前合同仍在快速演进，完整拆表会扩大迁移和兼容面。选择少量稳定热字段能获得主要查询收益，同时保留 JSON 演进能力。

### 继续在服务层筛选分页

拒绝。该方案的内存和解析成本随租户总 Run 数线性增长，且无法利用数据库索引。

## 后果

- 每个写路径必须同步维护派生列；测试通过旧库迁移、重复启动零更新和查询计划索引命中来防止漂移。
- 新列和索引是加法迁移，上一版本会忽略它们，因此通常可以只回退程序而保留当前数据库。
- 只有在迁移损坏且上线后没有新 Run、动作或 Provider 副作用时，才允许恢复发布前数据库快照。

## 回退

优先把 `current` 指回上一 release 并保留现有数据库。若必须恢复数据，先停止服务、保留失败现场副本，再恢复已经通过完整性检查的停机快照；不得覆盖上线后已产生有效业务或计费副作用的数据库。
