# ADR-002：使用租户绑定的分离服务凭据

## 状态

Accepted

## 日期

2026-07-23

## 背景

PPT Agent 只监听回环地址，由宿主服务端调用。早期实现使用一个共享 Token，同时信任请求头中的租户和角色；同一个 Token 还被复用于 PPT Agent 调用 FrameFlow 内部 API。这样无法证明 Token 属于哪个租户，也无法阻止普通调用方声明管理员角色，入站凭据泄露还会扩大到出站接口。

## 决策

- 每个服务凭据绑定一个确定的 `tenantId`，请求头租户必须与凭据配置一致。
- 普通 API Token 和管理员 API Token 必须分离；角色由匹配到的 Token 派生，不接受普通 Token 的管理员声明。
- `externalUserId` 和可选 `externalProjectId` 仍由受信宿主传入，但创建 Run 时最终持久化认证后的宿主上下文。body 中显式提供的项目或角色若不一致，返回 `403 HOST_CONTEXT_MISMATCH`。
- PPT Agent 调用 FrameFlow 附件与预算接口时使用独立的 `FRAMEFLOW_INTERNAL_TOKEN`，不复用任何入站 Token。
- 创建和动作请求按 `tenantId + externalUserId` 使用独立的进程内固定窗口限流。默认创建每分钟 10 次，普通及管理员动作每分钟 60 次；超限返回 `429` 和 `Retry-After`。

## 备选方案

### 共享 Token 加角色请求头

拒绝。请求头不是权限来源，持有普通 Token 的调用方可以直接声明管理员角色。

### 由 PPT Agent 签发用户 JWT

暂不采用。当前信任边界是宿主后端到回环服务，PPT Agent 不是用户身份提供方。引入用户 Token 签发、轮换和撤销会重复宿主能力。

### 使用 Redis 做分布式限流

暂不采用。当前生产拓扑是单个 systemd 实例，进程内限流足以保护写入口且不增加外部依赖。扩展为多副本前必须改为共享限流存储。

## 后果

- 生产环境需要三个互不相同的服务端 Token，并协调 FrameFlow 内部接口先接受新的出站 Token。
- 限流在进程重启后重置，也不跨实例聚合；它是入口保护，不是账务额度或计费控制。
- 回退旧版本时，FrameFlow 必须在回退窗口内继续接受旧版本使用的出站凭据。
- 服务仍只允许监听回环地址；这些凭据边界不能替代网络隔离。

## 回退

代码可回退到上一 release，但不得删除或复用新凭据。回退前确认 FrameFlow 仍接受旧版本的出站 Token，并恢复上一版权限 `600` 的环境文件；关闭回退窗口后再撤销旧凭据。
